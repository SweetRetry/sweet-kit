# 反馈与通知

反馈形态由**用户是否需要在原处修改输入**决定，不由消息严重程度决定。

## 1. 选择判据

- 反馈绑定到某个需要用户修改的具体输入 → **inline**，就地放在该控件旁。
- 反馈是操作的结果，输入无需修改 → **toast**，用户看到即可，重试入口仍在原处。
- 反馈是持续状态而非事件 → **空状态占位**或**页面级错误态**。

| 场景                                     | 形态                        |
| :--------------------------------------- | :-------------------------- |
| 字段校验、表单字段级错误                 | 字段下方 inline             |
| 对话框内提交失败且需修正输入             | 对话框内 inline             |
| 操作失败但输入无需修改（上传、保存、支付） | toast.error                 |
| 操作成功确认                             | toast.success               |
| 异步长任务完成（生成、导出）             | toast，同 `id` 承接等待态   |
| 批量操作部分失败                         | toast.warning，带成功/失败数 |
| 后台连接中断与恢复                       | toast，固定 `id` + `dismiss` |
| 列表或页面无数据                         | 空状态占位                  |
| 页面级加载失败                           | 页面级错误态 + 重试         |

## 2. 越界禁令

- **同一动作只给一种反馈**：不要既 toast 又在原地报错。
- **需要用户修改某个字段的错误不得只用 toast**：toast 会消失，用户失去修正入口。
- **「暂无数据」不得用 toast**：空是持续状态。
- **局部提交的等待态不得用 `toast.loading`**：用触发控件内的 spinner；只有跨页面、原上下文已消失的等待才由 toast 承接。
- **成功不得用 dialog 或 alert 打断**。
- **toast 只承载一句话**：`description` 是一句补充，更长内容留在原地。

## 3. 实现约定

- 需要就地更新的长任务用 `toast.loading` 取得 `id`，结束后以同一 `id` 转为 success/error，覆盖而非叠加。
- 长期驻留的状态类提示用固定 `id`，恢复时 `toast.dismiss(id)`。
- inline 错误使用 `role="alert"`；字段级错误预留最小高度，避免推挤下方内容（见 [UI Stability](stability.md) §3）。

## 验收清单

- [ ] **形态正确**：需修正输入的错误在字段旁，操作结果类用 toast。
- [ ] **不重复**：同一动作只有一种反馈形态。
- [ ] **状态归位**：空数据用空状态占位，页面级失败有持续可见的错误态与重试。
- [ ] **实例唯一**：toast 用 `id` 复用而非叠加。
